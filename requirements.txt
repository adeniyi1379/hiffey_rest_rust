Part 1: Owner View (What the System Must Do) 
1.1 Purpose 
Give the restaurant a fast, simple point-of-sale system that records every sale, tracks how much cooked 
food, pastry and drink is available and sold, records which worker handled each sale, and keeps 
working when the internet is down. Raw ingredients are not tracked. 
1.2 In scope and out of scope 
• In scope: menu and packs, order taking, discounts, VAT, manual payment recording (cash, bank 
transfer, card on a separate machine), receipts, cooked-food and drink stock, worker accounts 
with generated PINs, roles, reports, offline operation, background cloud synchronisation. 
• Out of scope for this build: manager web application (designed later), automatic bank payment 
confirmation, raw-ingredient and recipe costing, customer loyalty, delivery orders, kitchen display 
screen, worker shifts and shift-based cash reconciliation (to be revisited after development). 
 
1.3 Key terms 
Term Meaning 
Spoon The one standard measure for food. 1 spoon means the same for every food item. The 
kitchen must use a standard serving spoon. 
Unit (count) Items sold by count: drinks (bottle/can/cup) and pastries. Dodo is counted in pieces. 
Pack A saved bundle of items with set quantities, sold with one tap (for example the Standard 
Pack). 
Custom plate A plate the cashier builds by entering the number of spoons per item. 
Batch A quantity of food the kitchen records as cooked (for example 150 spoons of jollof). 
Stock ledger The permanent list of every stock movement (cooked, sold, wasted, adjusted). The 
balance is calculated from it. 
Terminal A / B Terminal A is the main PC that holds the data. Terminal B is the second PC that connects 
to A. 
 
1.4 How the two terminals work 
• Terminal A runs the shop database and the point-of-sale screens. Terminal B shows the same 
screens and connects to A over the shop network. 
• Both terminals see the same menu, stock and sales at the same time. 
• If Terminal A is switched off or fails, Terminal B cannot make transactions until A is back. This is a 
deliberate design decision. 
• Internet (Starlink) is only needed to copy data to the cloud. Selling does not need internet. 
• Recommended: a UPS (battery backup) for Terminal A, the router and the Starlink unit.

Workers and roles (USR) 
ID Requirement 
USR-1 Owner or manager creates a worker by entering the worker's name. The system generates a unique PIN

USR-8 Important actions (sale, void, discount, price change, stock change, reprint, login, PIN reset) are logged

1.6 A typical day 
• Morning: manager logs in, checks prices, discounts and VAT setting. Kitchen lead enters the 
cooked batches. Cashiers log in with their PINs. 
• During service: cashiers take orders using packs or custom plates, record payment, print 
receipts. Stock falls live; items go "sold out" automatically. Extra batches are added when more 
food is cooked. 
• Close: wastage is logged, remaining food is counted, manager reviews the day report, backup 
runs and sync completes when internet is available.

Part 2: Technical Design (How It Will Be Built) 
2.1 Architecture 
Component Runs on Role 
POS app (Tauri) Terminal A and B Desktop window with the Rust-based UI. Installed on both PCs. 
Local server (axum) Terminal A only Business logic and LAN API. Only process that writes to the 
database. 
Database (SQLite) Terminal A only Source of truth during operation. 
Sync worker Terminal A only Background task that pushes data to the cloud when internet is 
available. 
Print service Each terminal Sends ESC/POS receipts to the local printer. 
Cloud API + database Cloud (later) Receives synced data; will feed the manager web app (React). 
 
• Run modes: at first launch each PC is set to "Server + Client" (A) or "Client" (B). 
• One code path for the UI: on both terminals the UI talks to the same LAN HTTP/WebSocket 
API. On Terminal A the address is localhost; on Terminal B it is the fixed IP of Terminal A. 
• Network: Terminal A has a fixed LAN address (static IP or DHCP reservation on the router). The 
server listens on the LAN only. 
• Failure behaviour: if Terminal B cannot reach A, it shows "Server offline" and blocks selling.

2.5 Core business rules 
Money and units 
• All money is integer kobo. No floating-point numbers anywhere in pricing. 
• Rounding happens once per order total step and is defined in pos-core (round half up to the 
nearest kobo). 
• Food items use spoon as the base unit. Count items (drinks, pastries, dodo) use pieces. The unit 
label is a setting. 
Pricing order (fixed sequence) 
• 1. Line price = quantity x unit price (or pack price: calculated sum of components, or fixed price). 
• 2. Apply the best applicable active discount to each line (see precedence below). 
• 3. Add packaging fee for takeaway if enabled. 
• 4. Apply VAT according to the global mode. 
• 5. Total = result of step 4. All amounts stored on the order for later reports. 
VAT formulas (rate in basis points, for example 750 = 7.5%) 
Added on top:  vat = round(net x rate_bp / 10000);  total = net + vat 
Inclusive:     net = round(gross x 10000 / (10000 + rate_bp));  vat = gross - net 
Here net is the amount after discounts and fees. The VAT rate is whatever the manager sets; it is never 
hard-coded. Confirm the correct rate and treatment with your accountant. 
Discount precedence (assumption to confirm) 
• Discounts do not stack by default. For each line the system applies the single discount that gives 
the customer the biggest saving, unless a manual manager discount is entered, which replaces it. 
• Scope specificity is item/pack, then category, then store-wide, used only to break ties. 
• Percent discounts round once per line. Fixed-amount discounts are shared across eligible lines in 
proportion to their value. 
Pack expansion and stock deduction 
• When a pack is sold, the order line stores the pack, and order_line_components stores each item 
and quantity as they were at that moment. 
• The same database transaction writes one stock_ledger row (negative) per component and 
updates stock_balances. 
• If any component lacks stock, the whole sale line is rejected with a clear message naming the 
item.

Stock ledger 
• Balance = sum of ledger quantities. stock_balances is a cached copy kept consistent inside the 
same transaction. 
• Voids and refunds add a positive "void_return" row only if the manager marks the food as 
returned to stock; otherwise the quantity is logged as wastage. 
• End-of-day count writes a count_diff ledger row so the balance matches reality, and keeps the 
difference for reports. 
Overselling protection 
• The sale is committed with BEGIN IMMEDIATE on SQLite, so only one terminal at a time can 
take the last portion. 
• The check "enough stock" and the deduction happen in the same transaction. 
Order numbers, voids and edits 
• Order number = terminal prefix + sequence, generated by the server inside the transaction. 
• Paid orders are immutable. A void creates a linked reversing record, with manager PIN, reason 
and audit entry.

2.7 Security and permissions 
• PINs are stored hashed with argon2. Session tokens are random and expire after inactivity or 
when the worker logs out. 
• PINs are generated by the system (random, 6 digits by default), never chosen by hand. The 
system checks that a new PIN is not already in use by another worker, because login uses the 
PIN alone. 
• Repeated wrong PINs cause a temporary lockout on that terminal and are logged. 
• Every endpoint checks the role on the server. The UI hiding a button is never the only protection. 
• Manager PIN prompts for voids and manual discounts are verified by the server. 
• The server listens only on the shop LAN. Optional TLS on the LAN can be added. 
• Cloud traffic uses HTTPS only, with a per-restaurant API key stored securely on Terminal A. 
• No endpoint deletes sales, payments or ledger rows. Corrections are new records. 
 
2.8 Printing 
• Receipts are built as ESC/POS commands for 58mm and 80mm thermal printers and sent 
through the Windows print spooler (USB or network printers). 
• print_jobs table keeps status and attempts. Failed prints retry and can be reprinted manually. 
• Each terminal prints to its own printer; the printer name is a local setting on each PC. 
• Receipt layout is configurable (business name, footer message, VAT line). 
 
2.9 Offline operation and cloud synchronisation 
Offline 
Selling depends only on the shop network and Terminal A. Starlink affects synchronisation only. 
Synchronisation design 
• Outbox: every change writes a row into sync_outbox in the same transaction as the change itself. 
• Worker: a background task on Terminal A sends batches to the cloud over HTTPS when a 
connection check passes, with retry and backoff. It resumes from where it stopped after any 
interruption. 
• Idempotent uploads: every record has a UUID, so sending the same record twice never creates 
duplicates. 
• Append-only events: sales, payments, stock movements, wastage and counts are only ever 
added, so the cloud never needs conflict resolution. 
• Master data: menu, packs, prices, discounts and settings are changed on Terminal A and 
pushed up. The cloud copy is read-only in this phase. 
• Status: sync_state feeds the on-screen indicator (synced, waiting with count, last success time). 
• Later: the cloud API (axum + PostgreSQL) accepts the batches; the React manager web app 
reads from it. 
 
2.10 Backup, recovery and failure behaviour

Internet (Starlink) down Selling continues. Data waits in the outbox and syncs when internet returns. 
Terminal A off or crashed Terminal B shows "Server offline" and cannot make transactions. When A 
restarts, B reconnects automatically. 
Terminal B off Terminal A continues alone.

2.11 Testing 
• Unit tests (pos-core): pricing, packs, discounts, VAT in both modes, rounding, stock ledger 
rules. These are the most important tests. 
• Integration tests: two simulated terminals selling the last portion at the same time; pack sale with 
a sold-out component; void and refund; end-of-day count. 
• Sync tests: internet cut halfway through a batch; duplicate sends; restart during sync. 
• Hardware tests: chosen printer models, paper-out, USB unplugged. 
• Pilot: run the system alongside paper records for several days and compare totals before full use. 
 
2.12 Build, installation and setup 
• Tauri bundler produces a Windows installer. Same installer for both PCs; first-run wizard selects 
Server + Client or Client. 
• First-run wizard on Terminal A creates the database, the owner account, business details, VAT 
setting and printer. 
• First-run wizard on Terminal B asks for the fixed address of Terminal A and tests the connection. 
• Continuous build in GitHub Actions; version number shown in the settings screen. 
• Database migrations run automatically at server start, after a backup.

Part 4: Assumptions and Open Items 
4.1 Decisions already made 
• Two Windows PCs with printers; Terminal A is server + client, Terminal B is client only. 
• If Terminal A is down, Terminal B cannot make transactions. 
• SQLite behind a Rust server on Terminal A; Tauri with a Rust UI framework for the desktop app; 
React for the later manager web app. 
• Payments are manual: cash, bank transfer, card on a separate POS machine. 
• One standard food unit (spoon); drinks and pastries use counted units. 
• VAT is a global manager setting, inclusive or added on top. 
• Manager web app is not part of this build. 
• No worker shifts for now. Workers have a name and a system-generated PIN, and every sale is 
linked to the worker. Shifts and shift-based cash reconciliation will be discussed after 
development. 
4.2 Assumptions to confirm 
• Dodo is counted in pieces (as in the Standard Pack example). 
• Discounts do not stack; the best single discount applies per line, and a manual discount replaces 
it. 
• Leptos is the Rust UI framework (recommended with Tauri). Dioxus is the alternative. 
• Takeaway packaging fee is optional and set by the manager. 
• Returned food after a void goes back to stock only if the manager marks it so; otherwise it is 
logged as wastage. 
• PINs are 6 digits by default (4-digit PINs are easier to guess).
